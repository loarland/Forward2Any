不校验：任何知道这个回调地址的人都能往里面发消息。 只适合内网、或者上游确实没法带密钥的情况。如果只能用这个，建议在上面配一条 IP 白名单，至少限制一下来源。
固定密钥：上游在请求头里带上一串约定的字符就行，最好接、也最常用。
请求头名密钥放在哪个头里，默认 X-F2A-Token，改成别的名字也行。
密钥两边约定好的那串字符。上游发的值必须和它完全一致。
上游要发的是：X-F2A-Token: 你的密钥
HMAC-SHA256 签名：拿密钥对原始报文算一次 HMAC-SHA256， 把十六进制结果放进请求头。报文只要被动过一个字节签名就对不上，所以比固定密钥安全。 GitHub、Gitea 的 Webhook 默认就是这个方式。
请求头名签名放哪个头，默认 X-Hub-Signature-256（跟 GitHub 一致）。
密钥你在上游填的那个 Webhook Secret，两边必须一样。
上游要发的是：X-Hub-Signature-256: sha256=<十六进制摘要>
HTTP Basic：标准的 Authorization: Basic base64(用户名:密码)，浏览器和 curl 都原生支持。
请求头名这里当用户名填。
密钥这里当密码填。
用 curl 测试就是：curl -u '用户名:密码' <回调地址>
保存后会得到一个回调地址 /hook/<路径标识>，把它填到发送方即可。 如果后台挂在了 Nginx 之类的反代后面，IP 白名单里要填反代的地址， 因为程序看到的是直接连上来的那个 IP。

邮件接收（IMAP 轮询）

只处理未读邮件，处理成功后标记为已读 —— 所以同一封邮件不会被转发两次， 但也意味着你在邮箱里手动标成已读的邮件不会被处理。 轮询间隔小于 10 秒会按 60 秒处理（对邮件服务器礼貌一点，也不容易被封）。
注意：选「不加密」时密码是明文传输的，只在可信内网里这么用。
